## 倒戈的开始：从 CC 到 opencode 再到 CodeX

### Claude Code, 我的白月光

在 12 月从 MOIW 回来之后，我折腾好了 CC，也正是进入了只看命令行不看 IDE 的时期。在[[2025-12-3rd_eating-dumplings-on-the winter-solstice|去年12月下旬]]的时候，因为我的 BDR 现地攻略组的账号有个统计抽选数据然后分析数据最后发布分析结果的栏目，因此这一部分就交给了 CC 进行处理。效果还是非常惊艳的。

![[25-to-26-my-ai-usage-history-20261122_04-03-03.webp]]

在那之后就开始光速的烧 token 环节：[[2025-12-4th_start-working-on-the-graduation-project|自建 new api]]、折腾 astrbot、[[2026-01-1st_welcome-to-2026|开始用 agent 测试 AI 烤肉]]、[[2026-01-2nd_maybe-the-last-test-week|利用 notebookllm 进行最后的期末复习]] ……

不得不说 CC 真的是我的 Agent 白月光，在当时确实是让我看到了核弹爆炸，只需要在命令行里敲好指令，然后就可以该干嘛干嘛去等着验收就好了。虽然中间可能我转去了别的地方或者换了 Agent，但 Claude Code 确实是我的启蒙人。

### 转向 opencode，但是……

在 1 月中的时候，我突然了解到了 opencode。

opencode 的爆火不是没有理由的，是因为 A÷ 这个公司也算是作恶习惯了，2026 年 1 月 5 日起陆续有用户反馈用 OpenCode 登录 Claude Max 后被封号；1 月 8 日至 9 日，Anthropic 正式在服务端收紧校验，拦截伪装成 Claude Code 的第三方 OAuth 请求。Claude Code 团队成员 Thariq Shihipar 随后公开表示，第三方工具使用消费级订阅违反服务条款（ToS）并会触发滥用风控，开发者只应通过 API 接入。

![[25-to-26-my-ai-usage-history-20261122_04-11-57.webp]]

因此社区逆反心理带来“史特莱珊效应”，在 Hacker News 等社区引发了强烈不满，有不少人指责 A÷ 在打造封闭花园而且强行绑定自家的 harness 产品。这个时候，不少的人就转向去了开源的 **opencode**。opencode 在 1 月两周内暴涨约 1.8 万 Star，到 2 月 GitHub Star 数达到 11.2 万。

而我也是其中一个。

刚开始事情还是很好的，在 opencode 中我可以接入各种各样的模型，然后还存在一个叫做 **oh-my-opencode** 的项目。其可以作为插件配合 opencode，把不同模型的优势发挥起来，比如 Claude 模型担任指挥，Gemini 模型担任前端，GPT 模型担任审查以及 coding 部分的工作。

很庆幸最开始的视频中，刚好有一部分的思路和 matt pocock 现在的技能包类似（尽管这么说听着有点蹭或者往自己脸上贴金的意思）matt pocock 的 grill-me 这个 skill 在 2 月底上线，虽然那个时候我还不知道此人是何许人也也没有用过他的 skill，但是好在 1 月份那会我就已经意识到了 grill 和让 AI 拷问自己明确需求而不是泛泛许愿的重要性。

不过优秀的工程思路总会趋同、汇合，matt 的这个思路其实早在 23 年就已经有人提出了，那个时候 Agent Coding 还没影呢。

![[25-to-26-my-ai-usage-history-20261122_07-07-06.webp]]

在我写这篇文章的时候已经是 26 年底，我还在用 matt 和 grok bot 工程师土豆姐的 pstack 两份工作流。说实话我也不知道未来的工作流会是如何的，各家 harness 和模型的发展速度都太快了，大胆在这里做一下以下猜测吧：

- **Claude Projects / DSH Super Agent 的单 Agent 交流、多 Agent 工作的结构可能会成为主流**：当前人类自己要并行不同的项目、功能或者同时处理 CI、和 Agent 交互，需要自己管理 session 和对应的线程。模型可以很厉害，但是人类管理不同的线程多了就会有很严重的负担。**同时普通的一般人没有类似管理上下文、切换 session 的知识**，他们往往会在一个 session 里聊天，或者把多个功能开发的请求一次性交给 Agent，而 Agent 想要易用，也为了实现最终的 AGI，简化使用方式，降低人类的使用负担是必然趋势。
- **文档最小化，Agent 不应该依赖文档，Code 是最有力的证据**：在过去我会使用类似 trellis 这样的开发工作流，但是用了 matt 的工作流之后我把 trellis 卸载了。主要一方面模型强了我把工作流又换了，另外 trellis 其实是 SDD 也就是 spec 驱动开发，**但问题是 spec 需要高质量的人工精心维护，不然 Agent 很容易跑偏**。而 matt 的 spec 和 ticket 都是一次性的，他也多次声明自己的工作流并非 SDD，spec 应当在完成了任务之后就废弃。**Agent 应当尽量小的依赖文档、注释，甚至没有必要的注释、文档就应当删除**。文档和注释是给人类读的，而注意力惊人的 AI 应当直接探索代码或者派子代理进行探索然后得出结论。加上文档需要频繁的维护更新，一旦过期对项目的影响可能是灾难性的，在大型项目上尤其明显。
- **让 AI 互相做对抗性审查可能效率更低**：这个观点其实不是来自我，而是 poteto 姐，一方面当前模型在你交付了它审查任务中可能会陷入“吹毛求疵”的情况，可能可以给你找到 bug 但是往往不严重甚至虚报，而且会消耗大量的 token；另外就是**验证大于审查**，相比于让两个概率模型互相扯皮，把精力放在确定性检查上才更好，包括严格的 Lint 规则、类型系统、让 Agent 自己把应用跑起来做真实的端到端/UI 测试，甚至使用形式化验证（如 TLA+、Lean）等等。

我不知道我说的这几个工作流或者 harness 的改变会不会在未来的几个月内出现或者成为趋势，we'll see

## 资产生成类的模型很好，但我还是不爱用

gpt-image-2 当时在四月底正式发布，在灰度的时候就已经感受到了这个模型相比于之前的谷歌大香蕉的强大之处。以至于在当时我在灰度的时候收集好了一部分案例在正式上线的第一天就发到了各个平台和论坛上。这个模型对于谷歌大香蕉来说还是太降维打击了，很快，大家也都开始使用这个模型来制作海报或者封面。

但是很快，就如同大语言模型刚开始写网站那会默认使用 tailwind css 默认的蓝紫渐变一样，GPT 生成的图片开始明显有了自己的特征和风格，以至于逐渐让我看到就开始反感。

我尝试在 pinterest 和 unsplash 上找到自己喜欢的画风和构图，然后通过当时有着最强大的视觉能力的模型来反向提炼画风、构图等确定生成图片风格的提示词，这也就是这篇帖子 https://linux.do/t/topic/2044964 。在站内也有相关的视频，也算是稍微摆脱了直接对着 gpt-image-2 这个模型生图造成的重复和同一的观感。

![[25-to-26-my-ai-usage-history-20261123_03-27-40.webp]]

**但是还是没能完全解决，GPT 生成的图像还是有奇怪的碎片和玻璃感，而且即使要求了生图的风格，还是能很明显的看出这个模型生成出来的图片是如何的**。

在 5 月份进入了公司之后，我在一家 MaaS 公司实习，如果说的不好听一些，就是中转站。我虽然是产品经理或者说产品运营，但是因为公司小，加上本质上老板招我进来的岗位其实是管培生，也就意味着我可能要一个人担任很多份工作，**其中评测上游渠道模型和对接口的一部分工作也落到了我的头上**。

除了传统的 LLM，其中让我叫苦不迭对的最麻烦的，大概就是字节的 seedance。但是这篇文章我并不想过多的讨论我对的如何痛苦，**而是即使公司给我提供了大量的 seedance 测试渠道，但是我还是不喜欢使用这样的视频生成模型**。而且我认为，如此类型的视频生成模型虽然短时间还不会被代替，但是未来很有可能 A÷ 以及梁文峰这种非必要不做资产生成模型的思路才是对的。为什么？

自从 opus5.5 出来之后，我们可以看到这个模型极好的审美能力和其使用如 remotion, hyperframes 这样框架制作视频的能力非常强大。如果配合类似 ElevenLabs 作为音效和合成人声、GPT 生图配合生成一些必要的图片作为装饰元素，然后再让我们的 opus 把这些东西组合起来，最后就可以制作出一期还不错的视频。

![[25-to-26-my-ai-usage-history-20261123_03-39-20.webp]]

虽然现在我们还是可以非常明显看出来代码合成视频的痕迹，但是我觉得这种思路反而是正确的。**首先是视频生成模型的不可控性和不可修改性**。不可控性很好理解，就是大家常说的“抽卡”；至于我说的不可修改，并不是指的是某些工作台的对视频进行局部修改的功能，而是通过代码制作的视频本身就有非常方便的通过自动化测试（如 Playwright）再反过来修改代码重新渲染视频的修改方式，这也更贴近我们人类实际制作视频的方式。

What if 模型可以调用的工具越来越多呢？我把生图、生音乐、生语音的模型已经交给过了 AI，让其制作几期视频，AI 只需要利用 css 和 js，就可以尽可能的发挥网页上能用代码展示的效果给我制作出对应的效果，**而且这是可控的**。当然现在我们还在使用一些基本的其他扩散式生成模型（比如生图，suno 等等）但是这些模型说不定也可以像代码做视频一样进一步被拆解呢？

打个比方说，Tripo 不知道大家有没有听过，这是一个 3D 建模的 AI，你只需要上传一张图片就可以生成一个模型。对于一些复杂曲面比如某些角色模型来说，这是不错的；但是涉及到硬模型（如车子、房子）而且需要尺寸精确的模型来说，这个时候 AI 操控建模软件如 Blender 则会有更好的表现。

![[25-to-26-my-ai-usage-history-20261123_03-42-01.webp]]

如果大胆想象——当然现在我觉得也确实可以大胆想象了，模型能力更强了，那么是不是以后连曲面模型也可以通过代码来制作了呢？那么剩余的扩散式生成模型或许将不再成为主力，而是辅助 LLM 来进行成品的制作，比如生图模型用于生成某些材质的贴图、Suno 这类直接生成音乐的模型完全可以由 AI 操控如 Studio One、Synthesizer V 这种软件来进行编曲、混音的调试。

> 这里我提到了视频制作、歌曲制作等内容，涉及到了 AI，这个部分我会放在后面来特地说说。

## 模块化 or DIY 的设计是对的：接触 Pi 之后

在 6 月底我开始尝试 Pi Agent，在刚开始我还在说这个东西如此的毛坯房配置起来实在是太麻烦也太难用了。然而现在的我除了 CC 和不敢反代的 agy 以外，最爱用的就是我已经配置好的 Pi 了。

Why Pi？正是因为极简的设计和当前 SOTA 模型本身就非常强大的能力，**使得极简 harness 有的时候可以以较低的成本拿下和复杂 harness 接近的成果**。打个不严谨的比方：同样的模型，在 Pi 上可以以 1 刀拿下 50 的分数；在 CC 上则需要以 5 刀拿下 60 的分数。

这个分数可能不一定严谨，但是大概是这个意思。以及有相关的 harness 评测网站在使用多个不同模型在多家 harness 上进行多轮跑分测试，也确实可以看到这个情况。

![[25-to-26-my-ai-usage-history-20261123_03-55-45.webp]]

另外就是定制化，即使是 CC 我们也可以看到其前不久还推出了 Mods 功能允许你一定程度上对自己的 APP 进行定制化修改，而极简 Agent 则修改起来会更加方便。一切皆插件化的形式可以让你方便的卸载以及安装。

**但是这样的极简化设计自然也存在问题**。DSH 还没有推出稳定版，一更新插件爆炸是常见的事情；Pi 过去说自己不打算做 MCP，但是在 1.0 版本之后还是把 MCP 这个功能给加上了，一方面有 A÷ 对 MCP 协议的优化，另一方面 CLI+skill 其实部分时候并不是 MCP 最好的代替；另外还有就是一些其实是挺刚需的功能，但是官方并不打算做，就只能依赖社区的开发者自己去维护，然后花很长的时间筛选沉淀出一个比较好用的插件，但这也终究不是官方会去针对性支持和维护的。我现在日益感觉 Pi 没有类似 background tasks 功能是一个很大的问题，说不定他们在支持了 subagent 之后，后台任务可能也是个要加上的功能。

感觉之后的产品（主要还是开源类的）插件化是一个比较好的思路。AI 飞速的发展会导致人人都有自己的想法，很多开源项目现在其实为了保证自己的代码质量和稳定性已经不接受外部的 issue 或者 PR 了，**但如果本身产品就是模块化设计的呢**？开发者只需要维护自己的仓库为一个核心，加入必要的功能支持，至于其他的部分只需要写好接口和文档，有想法的人只需要在上面进行插件的开发，形成类似的插件市场，既不会有一堆 AI 生成的屎山来污染核心代码，又可以看到社区的各种创意和需求。

## AI Slop 与 AI 生成垃圾：感觉我正处于一场死亡搁浅

回到我最开始所说的：为什么我在享受 AI 便利、认为无法回到没有 AI 的那个时候、肯定 AI 技术的同时，对一部分使用 AI 用途感到深恶痛绝的原因。

首先最直观的感觉还是来自产品与工程，得益于 AI，现在人人都可以当产品经理，开发的门槛早就大大降低了，**但每个人的工程能力和审美底线是完全不一样的**。结果就是市面上涌现了大量产品级的 AI Slop，很多东西根本没经过细心的打磨和优化就被直接端了上来。而且因为搓一个东西的成本太低，重复造轮子的情况其实也越来越多了。

![[25-to-26-my-ai-usage-history-20261123_04-50-02.webp]]

这种泛滥不只停留在代码和产品里，我日常使用的社交媒体也在被肉眼可见地污染。比如在 B 站，经常能看到有人养类似大肥鱼这样的 AI 账号，放进评论区之后自己却不管不顾，任由它们在别人的视频底下胡乱回复、留下一地鸡毛——说难听点，这和遛狗不牵绳、放任它在公共场合到处拉屎没什么区别。明明有私信的接口却不使用，我无法理解。

**而最让我无法忍受的还是艺术创作**。

**我从来不反对在创作里使用 AI**，我今年本身有无数个视频都是这样做的。如果你想做一首歌，用 AI 辅助编曲、混音，甚至用 sv 这样的虚拟歌姬来完成演唱，这些都没问题；如果你想讲一个故事，无论载体是小说、Galgame 还是短剧，让 AI 帮忙配乐、生成一些画面素材，也完全可以接受。但最核心的创意部分——歌曲的词曲、故事的剧本——必须是你自己完成的。如果连这部分都交给了 AI，那这件事就彻底失去了“你”去创作的意义，生成出来的不过是一堆流水线上的 AI Shiiiit。

可现实相反。为了保量而放弃质量的内容现在越来越多，互联网的节奏本来就已经够快了，随着红果这类短剧平台的兴起，再叠加 AI 的批量生产，各种毫无营养的快餐小短剧源源不断地被制造出来，而且依然有大把人买单。速度越来越快，大家也就越来越没有时间和耐心沉下心去欣赏真正的作品。我已经习惯性的看到了 AI 封面就提前有个大概的刻板印象，因为很有可能点进去大概率不会是我想看到的作品；即使抛开 AI 封面不谈，有很多视频，我相信看的多了的人自然也有很明显的感觉，只需要不超过 10s，你就知道这视频有没有用心做了，真的，不用更久了。

很遗憾的是我也不是没干过。

如果你关注了我而且真的能读到我这篇文章的这里，你应该知道之前我也做过一个类似 AI Roleplay / AI Companion 的项目——**eidolon-sc**，但越做到后面，我越觉得我不应该真的把它当成一个“陪伴”或者“角色扮演”的产品来对待。

把某些游戏或动画里的台词全部提取出来，让模型去提炼、蒸馏出一套人设再进行扮演，听起来感觉是不错的吧？可我们都很清楚，它的本质终究只是一个 Transformer。当你把大模型和你的技术栈有个七七八八的了解之后，你很难真的把它当成一个有温度的人来看待，无非只是种种工具的结合罢了。

陪伴和角色扮演的核心，本来就是它和你说的话、是你们之间共同生发出来的故事——而在这个核心上，AI 依然远不如真实的人类甚至宠物。**人与人之间的交流才是最宝贵的**。这也是为什么我最近没有再给那个项目更新更多功能：作为一个测试性的产物，它已经验证了我把各个工具组合起来能跑出不错的效果，既然验证完了，那就到此为止吧，我不想再亲手制造更多的AI 泔水。

《死亡搁浅》的开头有一段话：

> 从前曾发生过一次爆炸……时间和空间在大爆炸那一刻诞生。从前曾发生过一次爆炸……有个星球在爆炸后诞生并开始自转。从前曾发生过一次爆炸……生命在爆炸后繁衍生息。后来又发生了一次爆炸……

![[25-to-26-my-ai-usage-history-20261123_05-03-09.webp]]

铺天盖地的 AI Slop、无人看管的 AI 账号、被算法和流水线催熟的快餐内容，就像游戏里不断落下的时间雨和荒野上四处游荡的 BT——酷似人类，但没有人类的温度。

但就像 sam 依旧会使用外动力骨骼和开罗尔打印机一样，技术爆炸已经发生了，我们不可能也没必要退回没有 AI 的年代。AI 是极好的工具，能帮我们扛起繁重的工程、跨越原本跨不过去的技术门槛；可它终究只是辅助你的工具，而不是替你思考的全自动配送机器人。

在这场噪声越来越大的死亡搁浅里，由人亲手打磨的产品、用心写下的故事，以及屏幕背后人与人之间真实的交流，才越像是安部公房那根珍贵的“绳子”。

![[25-to-26-my-ai-usage-history-20261123_05-04-45.webp]]

这大概就是我在 2026 年底，对 AI 最大的感受了。
